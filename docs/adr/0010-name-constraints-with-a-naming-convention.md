# 0010. Name constraints with a naming convention

- **Status:** Accepted
- **Date:** 2026-11-01

## Context

Alembic's first autogenerated migration created foreign keys without names.
SQL Server assigns unnamed constraints random names, such as
`FK__printings__set_i__3B75D760`, and every database gets a different one. A later
migration that drops or alters a constraint has to name it, so it would work in
some environments and fail in others.

Names are assigned when a constraint is created, so this had to be fixed before the
first migration was applied anywhere.

## Decision

Set a naming convention on `SQLModel.metadata` in `models.py`, before any table is
defined:

| Type        | Pattern | Example |
|-------------|---------|---------|
| Index       | `ix_<table>_<column>` | `ix_printings_set_id` |
| Unique      | `uq_<table>_<column>` | `uq_sets_code` |
| Foreign key | `fk_<table>_<column>_<referred table>` | `fk_printings_set_id_sets` |
| Primary key | `pk_<table>` | `pk_printings` |

## Alternatives considered

- **Naming each constraint by hand:** works, but easy to forget, and autogenerate
  won't remind you.
- **Accepting generated names:** fine until the first migration needs to change a
  constraint.

## Consequences

- Every environment gets identical, readable constraint names, verified in SQL Server
  through `sys.foreign_keys`.
- Migrations can reliably drop or alter constraints by name.
- The convention must stay in place; changing it later means renaming existing constraints.
