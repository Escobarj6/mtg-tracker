# 0011. Manage schema changes with Alembic

- **Status:** Accepted
- **Date:** 2026-11-01

## Context

The schema will keep changing, and once real data exists, tables can't be dropped
and recreated. Every environment (local, CI, staging, production) must end up with
the same schema, applied in the same order. The target team uses Alembic.

## Decision

Use **Alembic** for all schema changes:

- `migrations/env.py` connects with the app's own `get_engine()`, so credentials come
  from `MTG_*` settings. `alembic.ini` contains no database URL.
- `target_metadata = SQLModel.metadata`, so `--autogenerate` drafts migrations by
  comparing the models with the database.
- The migration template uses modern typing and imports `sqlmodel`; post-write hooks
  run `ruff format` and `ruff check --fix` on every generated migration.

## Rules

- **Read every autogenerated migration before applying it.** Autogenerate is a draft,
  not a guarantee; reading it is how unnamed foreign keys were caught (see 0010).
- **Drafts can change; history can't.** A migration that exists only locally and has
  not been pushed can be edited or regenerated. Once it has been applied anywhere else
  or merged, never edit it; write a new migration instead.
- Test the downgrade path (`alembic downgrade` then `upgrade`) before merging.

## Alternatives considered

- **`SQLModel.metadata.create_all()`:** creates missing tables, but can't alter
  existing ones and keeps no history.
- **Hand-written SQL scripts:** full control, but no autogenerate and no built-in
  version tracking.

## Consequences

- Each database records its version in the `alembic_version` table, and `upgrade head`
  applies only what's missing.
- Schema changes are reviewed in pull requests like code.
- Setup gains a step: `uv run alembic upgrade head`.
